# BRD — MediCard Health Cashless Hospitalization & Settlement Platform

Business Case: BC-AINE-017 · Domain: Insurance — Health Cashless · Status: **Approved** (gate 1)
Source: capstone brief sections 3, 5 and 6. Interview answers were taken from the brief; open
points were resolved as explicit decisions in section 13 and carried into `specs/*_spec.md`.

## 1. Executive Summary

MediCard is a multi-party platform that lets a health insurer run cashless hospitalization at its
network hospitals: eligibility lookup, pre-authorization, admission tracking, final-bill
submission, settlement to the hospital, and audit. The customer, hospital, insurer adjudicator and
insurer admin each have their own role-separated view. All production code is generated by Claude
Code agents through the Claude Harness Engine.

## 2. Problem Statement

Cashless hospitalization today relies on phone calls, e-mailed forms and manual adjudication.
Hospitals wait hours for pre-auth decisions. Bills that exceed the approved amount are only
discovered at discharge. Settlement math is done in spreadsheets, and override decisions leave no
trustworthy audit trail. Customers cannot see where their case stands.

## 3. Target Users

| Persona | Role code | Primary goal |
|---|---|---|
| Policy holder / member | `CUSTOMER` | See own coverage, track own case timeline, see settlement breakdown |
| Network hospital desk | `HOSPITAL` | Check eligibility, raise pre-auth, record admission / procedures / final bill |
| Insurer adjudicator | `INSURER` | Work the manual review queue, decide pre-auths, settle discharged cases |
| Insurer admin | `ADMIN` | Maintain network / products / versioned coverage rules, override auto-rejections, view reports |

## 4. Success Metrics

| Metric | Target |
|---|---|
| Auto-decided pre-auths (rule-eligible) | 100 % decided at submission (0 s human wait) |
| Pre-auth turnaround (manual) | Measured by the turnaround report; baseline captured from seed data |
| Settlement math defects | 0 — every settlement satisfies `settlement_amount ≥ 0` and the cap rule |
| Final bills above `pre_auth_amount + buffer` accepted | 0 |
| Overrides without actor / timestamp / reason audit record | 0 |
| PHI strings found in application logs | 0 |
| Health endpoint after startup | HTTP 200 within 1 s |

## 5. Scope

**In:** customer registration and policy linking, coverage view, eligibility lookup, pre-auth
submission and lifecycle, rule-driven auto-approval, adjudicator workbench with query workflow,
admin override with audit, admission / procedure / final-bill updates, bill-cap validation,
settlement calculation with a stubbed payment trigger, case lifecycle and timeline, stubbed
customer notifications, network hospital / product / coverage-rule admin, reports.

**Out (per brief 6.3):** real HIS / EMR / EHR integration, real payment rails, a real ICD-10 master
(a small static stub is used), fraud detection, multi-currency, production deployment / secret
management / multi-region.

## 6. MVP Definition

The ten acceptance criteria AC-01 … AC-10 and NFR-01 … NFR-08 of `specs/app_spec.md`, runnable
locally with one command and seeded with synthetic data.

## 7. Alternatives Considered

| Decision | Options | Chosen | Rationale |
|---|---|---|---|
| Backend | Spring Boot, ASP.NET, FastAPI, Express | **Python + FastAPI** | Learner background; Decimal money type; pytest + import-linter |
| Database | H2/SQLite, RDBMS, NoSQL | **SQLite** | Zero-install local run; triggers enforce append-only tables |
| Frontend | React, Angular, Vue, server-rendered | **React (Vite, TypeScript)** | Responsive SPA served by the backend |
| Migrations | ORM auto-create, numbered SQL files | **Numbered SQL files + checksum ledger** | Makes NFR-05 (append-only migrations) mechanically checkable |
| Auth | External IdP, session cookies, signed bearer token | **HMAC-signed bearer token (stdlib)** | No secret infra needed (out of scope); role boundary sits at the controller |
| CI | GitLab CI, GitHub Actions | **GitLab CI** | Preferred for Virtusa; Claude Code wired into merge-request pipelines |

## 8. Technical Architecture

Layered: `domain → config → repository → service → api → ui` with one-way imports, enforced by
import-linter, the harness `check-architecture` hook and `tests/architecture/`. See
`docs/architecture.md`.

## 9. Data Model Overview

Customer, Member, Policy, PolicyProduct, CoverageRuleVersion, NetworkHospital, User, PreAuth,
PreAuthDecision (append-only), ClaimCase, CaseEvent (append-only), Procedure, FinalBill
(append-only), Settlement (append-only), Notification, AuditRecord (append-only).

## 10. External Integrations

None real. Payment trigger and customer notification are stubs that write records.

## 11. Edge Cases & Constraints

- Money in fixed-point Decimal, 2 decimal places, ROUND_HALF_UP (NFR-01).
- Deductible larger than the admissible amount must never yield a negative settlement (AC-07).
- Final bill exactly equal to `pre_auth_amount + buffer` is accepted; one paisa more is rejected (AC-06).
- An estimated cost exactly equal to the auto-approval threshold auto-approves (AC-05).
- Invalid case transitions raise `InvalidClaimStateException` (AC-08).
- Settled cases cannot be mutated (NFR-08).
- A hospital must never see another hospital's cases (NFR-04).
- Diagnosis / procedure text must never reach logs (NFR-03).

## 12. UI Context

An internal-tool style portal with four role workspaces. Functional focus. It must be responsive,
so mobile-width layouts stack vertically.

## 13. Open Questions → Resolved Decisions

| # | Question | Decision |
|---|---|---|
| D-1 | What is the "policy cap" in AC-05? | `min(per_claim_cap, remaining_sum_insured)` |
| D-2 | How is co-pay applied in AC-07? | On the post-deductible amount, so the result is never negative |
| D-3 | Which state does an excluded diagnosis produce? | Auto `REJECTED` by `SYSTEM` (overridable per AC-10) |
| D-4 | Which state does an unknown diagnosis code produce? | Auto `QUERY_RAISED` (incomplete submission) |
| D-5 | When is a claim case created? | At pre-auth submission, in state `PRE_AUTH` |
| D-6 | What happens to a rejected pre-auth's case? | It may move `PRE_AUTH → CLOSED` |
